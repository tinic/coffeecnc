# G0759: first machine target

The owner selected the **G0759** for CoffeeCNC's first machine integration on 14 November 2026. Machine definitions live in [tinic/linuxcnc](https://github.com/tinic/linuxcnc), separately from this application. Other machines must remain configurable without forks of the UI or controller core.

This is a static inspection of source revision [`949d67ffa6e1c5dafc2751f651297b4076fa792b`](https://github.com/tinic/linuxcnc/tree/949d67ffa6e1c5dafc2751f651297b4076fa792b/configs/G0759). It does not establish the currently deployed configuration, LinuxCNC version, physical travel, or measured tool assemblies. No hardware was contacted or operated.

## HAL and peripheral boundaries

The primary HAL loads a **Mesa 7i76E through `hm2_eth`**, with three step generators and a spindle encoder. `custom.hal` then replaces the step-generator position-feedback sources with `rp2040-encoder.0.position-{0,1,2}`; its scales are −0.005, +0.005 and +0.005. Preserve that configured feedback chain. CoffeeCNC should read LinuxCNC's resulting actual position, not derive it from step commands or talk directly to the encoder. The RP2040 userspace component must be present on the target host; its implementation is not included in this repository snapshot.

The VFD is controlled by the userspace **`svd-ps_vfd`** component on a configured serial device. The repository contains its C source. The frontend should request spindle state through LinuxCNC; device paths, maximum frequency and transport stay in the machine configuration. The existing HAL also has `not` and `limit1` components, so additional application wiring must avoid duplicate module loads and numbered-instance collisions. [Custom HAL](https://github.com/tinic/linuxcnc/blob/949d67ffa6e1c5dafc2751f651297b4076fa792b/configs/G0759/custom.hal), [VFD source](https://github.com/tinic/linuxcnc/blob/949d67ffa6e1c5dafc2751f651297b4076fa792b/src/svd-ps_vfd.c).

A physical input supplies external E-stop, and another supplies `motion.probe-input`. Spindle encoder feedback is converted from revolutions/second to RPM and absolute RPM; `spindle.0.at-speed` is driven by a `near` comparison. The embedded RPM widget consumes `spindle-vel-fb-rpm-abs`. The current CoffeeCNC protocol exposes commanded spindle RPM only; actual RPM, at-speed and probe state need explicit optional status fields before equivalent UI indicators can be implemented. Unavailable feedback must remain distinguishable from a reported zero. [Main HAL](https://github.com/tinic/linuxcnc/blob/949d67ffa6e1c5dafc2751f651297b4076fa792b/configs/G0759/G0759.hal), [RPM widget wiring](https://github.com/tinic/linuxcnc/blob/949d67ffa6e1c5dafc2751f651297b4076fa792b/configs/G0759/rpm.hal).

`custom_postgui.hal` connects manual tool change to `gmoccapy.toolchange-*`, loops prepare to prepared, and refers to gmoccapy tool-offset/spindle-display pins. A CoffeeCNC-specific fragment must connect the application's manual-change handshake while preserving the intended prepare loop. Do not run both frontends' handshake outputs together. This file is reached through `postgui_call_list.hal`, so migration must follow the include chain. [Post-GUI wiring](https://github.com/tinic/linuxcnc/blob/949d67ffa6e1c5dafc2751f651297b4076fa792b/configs/G0759/custom_postgui.hal), [call list](https://github.com/tinic/linuxcnc/blob/949d67ffa6e1c5dafc2751f651297b4076fa792b/configs/G0759/postgui_call_list.hal).

## Adapter gaps found in the first review

Compared with CoffeeCNC PR #6 at `7694a18`:

- `MachineConfig` accepts this XYZ/mm kinematics shape, but **rejects the INI's spindle configuration**. It requires `[SPINDLE_0] MAX_FORWARD_VELOCITY` or `[DISPLAY] MAX_SPINDLE_0_SPEED`; neither is present. The integration profile must explicitly map the G0759 VFD ceiling or provide a normalized standard setting. A generic fallback to the custom key would assign semantics to unrelated machines' sections.
- The loader currently collapses jogging to a global ceiling. It does not load the configured increment list into its `MachineConfig`, or carry distinct X/Y/Z jog ceilings there. Complete the hello/config propagation and native per-axis validation before presenting those settings as supported.
- The current core requires homing for some actions despite this machine's `NO_FORCE_HOMING` setting. Retain current checks until the machine workflow and capability contract are decided; do not silently relax them based on a name or hide the disagreement.
- The existing gmoccapy post-GUI file cannot be reused unchanged. The CoffeeCNC jog-stop/watchdog wiring must be composed with the machine's existing components and HALUI inputs.
- The configured tool table cannot populate realistic cutter geometry. Do not import gmoccapy preference values such as a remembered in-spindle tool as controller truth.

`NmlPort` currently fills `Axis.machine` from `motion.traj.actualPosition`, normalized to mm. The preview anchors the tool body at that value minus the active tool offset once, matching the protocol's tool-tip convention. Work-origin transforms and the cutter's physical overall length do not enter this anchor.

## Keep machine support extensible

Use these boundaries for the next implementation:

1. **LinuxCNC remains the configuration authority.** Load axes, kinematics, units, limits and state from the selected INI/controller. A machine integration profile records any explicit custom-key mappings, optional signals and extra UI features; ordinary widgets consume capabilities rather than machine names.
2. **Keep launch/HAL integration separate.** The G0759 owns its Mesa, encoder, VFD and physical input wiring. CoffeeCNC owns its application pins and handshake contract. Preserve the gmoccapy setup alongside a separately reviewable CoffeeCNC configuration.
3. **Scope persistence by machine identity.** Native tool-model assignments, job attachments and preferences need a stable configuration identity, not just `MACHINE = G0759` or a T number. Physical stick-out is also setup-specific. Browser-only defaults remain a development convenience.
4. **Advertise only implemented capabilities.** Initially support XYZ identity kinematics and manual tool changes. Other machine layouts should produce a specific unsupported-capability explanation. Later rotary axes, gantries, tool changers and spindle orientations require richer contracts, not hidden G0759 assumptions in the renderer.
5. **Qualify a derived simulation first.** Exercise the G0759's units, asymmetric rates, increments, overrides, empty-dimension tool table and manual-change flow in a hardware-free fixture. Do not launch the real HAL in tests: it loads network and serial hardware drivers. Retain the worker/lease and delayed-jog-start tests before live-shell wiring.

The next reviewable increment is configuration/profile coverage and a G0759-shaped simulation fixture, followed by native WebKitGTK qualification. Physical homing behavior, travel and tool measurement remain machine commissioning questions, not facts established by this source review.
