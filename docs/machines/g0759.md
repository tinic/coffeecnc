The owner selected the **G0759** for CoffeeCNC's first machine integration on 14 November 2026. Machine definitions live in [tinic/linuxcnc](https://github.com/tinic/linuxcnc), separately from this application. Other machines must remain configurable without forks of the UI or controller core.

## HAL and peripheral boundaries

The primary HAL loads a **Mesa 7i76E through `hm2_eth`**, with three step generators and a spindle encoder. `custom.hal` then replaces the step-generator position-feedback sources with `rp2040-encoder.0.position-{0,1,2}`; its scales are −0.005, +0.005 and +0.005. Preserve that configured feedback chain. CoffeeCNC should read LinuxCNC's resulting actual position, not derive it from step commands or talk directly to the encoder. The RP2040 userspace component must be present on the target host; its implementation is in [tinic/rp2040-encoder](https://github.com/tinic/rp2040-encoder), not in this repository. Since 22 November 2026 the machine runs version 3.0.0 of its firmware and component, which also report each scale's reference pulse (`ref-count-N`, `ref-position-N`); `custom.hal` sets `sign-N` to −1, which that version needs for the same axis directions, and no longer zeroes the encoder count when LinuxCNC starts.

The VFD is controlled by the userspace **`svd-ps_vfd`** component on a configured serial device. The repository contains its C source. The frontend should request spindle state through LinuxCNC; device paths, maximum frequency and transport stay in the machine configuration. The existing HAL also has `not` and `limit1` components, so additional application wiring must avoid duplicate module loads and numbered-instance collisions. [Custom HAL](https://github.com/tinic/linuxcnc/blob/949d67ffa6e1c5dafc2751f651297b4076fa792b/configs/G0759/custom.hal), [VFD source](https://github.com/tinic/linuxcnc/blob/949d67ffa6e1c5dafc2751f651297b4076fa792b/src/svd-ps_vfd.c).

A physical input supplies external E-stop, and another supplies `motion.probe-input`. Spindle encoder feedback is converted from revolutions/second to RPM and absolute RPM; `spindle.0.at-speed` is driven by a `near` comparison. The embedded RPM widget consumes `spindle-vel-fb-rpm-abs`. CoffeeCNC's protocol and panel distinguish commanded RPM from optional measured RPM, at-speed and probe status. The native shell now publishes configured optional HAL feedback to the panel, with simulation coverage. Unavailable feedback remains distinguishable from a reported zero. [Main HAL](https://github.com/tinic/linuxcnc/blob/949d67ffa6e1c5dafc2751f651297b4076fa792b/configs/G0759/G0759.hal), [RPM widget wiring](https://github.com/tinic/linuxcnc/blob/949d67ffa6e1c5dafc2751f651297b4076fa792b/configs/G0759/rpm.hal).

`custom_postgui.hal` connects manual tool change to `gmoccapy.toolchange-*`, loops prepare to prepared, and refers to gmoccapy tool-offset/spindle-display pins. A CoffeeCNC-specific fragment must connect the application's manual-change handshake while preserving the intended prepare loop. Do not run both frontends' handshake outputs together. This file is reached through `postgui_call_list.hal`, so migration must follow the include chain. [Post-GUI wiring](https://github.com/tinic/linuxcnc/blob/949d67ffa6e1c5dafc2751f651297b4076fa792b/configs/G0759/custom_postgui.hal), [call list](https://github.com/tinic/linuxcnc/blob/949d67ffa6e1c5dafc2751f651297b4076fa792b/configs/G0759/postgui_call_list.hal).

## Keep machine support extensible

Use these boundaries for the next implementation:

1. **LinuxCNC remains the configuration authority.** Load axes, kinematics, units, limits and state from the selected INI/controller. A machine integration profile records any explicit custom-key mappings, optional signals and extra UI features; ordinary widgets consume capabilities rather than machine names.
2. **Keep launch/HAL integration separate.** The G0759 owns its Mesa, encoder, VFD and physical input wiring. CoffeeCNC owns its application pins and handshake contract. Preserve the gmoccapy setup alongside a separately reviewable CoffeeCNC configuration.
3. **Scope persistence by machine identity.** Native tool-model assignments, job attachments and preferences need a stable configuration identity, not just `MACHINE = G0759` or a T number. Physical stick-out is also setup-specific. Browser-only defaults remain a development convenience.
4. **Advertise only implemented capabilities.** Initially support XYZ identity kinematics and manual tool changes. Other machine layouts should produce a specific unsupported-capability explanation. Later rotary axes, gantries, tool changers and spindle orientations require richer contracts, not hidden G0759 assumptions in the renderer.
5. **Qualify a derived simulation first.** Exercise the G0759's units, asymmetric rates, increments, overrides, empty-dimension tool table and manual-change flow in a hardware-free fixture. Do not launch the real HAL in tests: it loads network and serial hardware drivers. Retain the worker/lease and delayed-jog-start tests before live-shell wiring.

## Reference-mark homing, 22 November 2026

Since this date the CoffeeCNC launch configuration homes on the reference (R) marks of the glass scales instead of in place, and has travel limits. The machine files are in [machine configuration PR #2](https://github.com/tinic/linuxcnc/pull/2); CoffeeCNC's part is in [PR #203](https://github.com/tinic/coffeecnc/pull/203). This section records what is configured, what the operator sees, and what was seen on the machine that day.

### Why a home switch is derived from the mark

Each scale has exactly one reference mark in its travel, so at power-up nothing says on which side of its mark an axis stands, and the machine has neither home nor limit switches. The realtime component `refmark` of the machine configuration (one instance per axis) remembers where a mark is once the encoder interface has seen it, and from then on acts as a home switch that is closed on one whole side of the mark, starting 3 mm before it. LinuxCNC's ordinary switch homing with `HOME_USE_INDEX` then finds the switch edge from either side at 5 mm/s and creeps onto the mark at 0.5 mm/s, always in the + direction; `refmark` clears the index handshake in the servo period in which the pulse count changes. The latched mark position differs by 0.02 to 0.03 mm between the two approach directions, which is why the last approach has one direction.

The scale count is not reset at the mark (`HOME_INDEX_NO_ENCODER_RESET`) and no longer at a start of LinuxCNC, so a mark stays known across restarts of LinuxCNC for as long as the encoder box is powered. After the controller has been powered up, each axis must cross its mark once, by a jog or by hand, before it can be homed.

| Protection | Where | What happens |
| --- | --- | --- |
| A stall during the home move | The scales are the position feedback of the joints | LinuxCNC's following error (`FERROR = 10`, `MIN_FERROR = 1` mm) |
| Home before the mark is known | CoffeeCNC's policy | The request is refused with the reason, nothing moves |
| The same from another program | `refmark.N.fault` to `joint.N.amp-fault-in` | Amplifier fault on the joint, the machine drops out |
| An index search that passes the mark by 3 mm without a pulse | `refmark.N.fault` | Amplifier fault on the joint |
| A latched mark that does not fit the axis position at its pulse (more than 3 mm apart), or that the interface has not delivered | `refmark` | The axis counts as not ready until it crosses the mark again |

### What CoffeeCNC does

`[COFFEECNC] REFERENCE_MARKS = yes` declares two bits per axis, which the machine's post-GUI file connects from `refmark`:

| Pin | Meaning | Panel and policy |
| --- | --- | --- |
| `coffeecnc.reference-mark-x`, `-y`, `-z` | The axis's mark has been found | While false the Home button reads "find mark", and `home` for that axis and for all axes is refused with "Move X across its reference mark first: homing cannot find it yet." |
| `coffeecnc.at-reference-mark-x`, `-y`, `-z` | The axis stands within 2 mm of its mark | The letter on the axis's Home button is red and the button reads "at mark", also with the machine off, so that an axis moved by hand can be stopped at its mark |

An axis whose mark is known and that is elsewhere reads "not homed", as before. Homing itself is LinuxCNC's: CoffeeCNC sends the same home command as for a machine with switches, shows "homing" while a joint homes and refuses jogs, MDI and program starts during that time.

### Operator's sequence

1. After power-up, move each axis across its reference mark: jog it with the machine on, or turn the handwheel with the machine off. The Home button changes from "find mark" to "not homed", and its letter is red while the axis is within 2 mm of the mark.
2. Switch the machine on and press Home for an axis, or Home all (Z, then X, then Y).
3. The axis goes to its mark from whichever side it is on and reads 0.000 when done.

Z's mark is 172 mm below the upper stop. Homing Z from above is configured to lower the head to about 3 mm below the mark before it creeps up onto it: the table and the tool must leave room for that.

### Measured travel

Measured once, with the operator driving each axis to both hard stops; positions are from the scales (0.005 mm per count).

| Axis | Travel between hard stops | Mark, approached in + | Hard stops in machine coordinates | Configured limits |
| --- | --- | --- | --- | --- |
| X | 403.965 mm | 224.110 mm from the negative stop | −224.110 and +179.855 | −222.11 to 177.855 |
| Y | 140.145 mm | 35.375 mm from the negative stop | −35.375 and +104.770 | −33.375 to 102.77 |
| Z | 261.520 mm | 172.370 mm below the upper stop | −89.150 and +172.370 | −87.15 to 160.5 |

The upper Z limit is not 2 mm inside its stop like the others. At 169.87 mm, the safe height Go to used under the first limit of 170.37, the head ran into the gears and chains. With the limit at 160.5 the default safe height and the end of a continuous Z+ jog are 160.0 mm.

The mark is machine zero on each axis. Work offsets and a tool-setter position taught before this date are in the earlier, arbitrary machine coordinates and have to be set again.

### What was seen on the machine

With all three marks known, the operator homed X, Y and Z. Read from HAL pins afterwards, each joint was homed without a fault and stood on the latched mark to the encoder count: X −36.525, Y −57.610 and Z −15.595 in encoder coordinates, equal to the latched values. After the change to machine zero at the mark and another homing, the panel showed X 0.000 and Y 0.000 with all three axes homed. The home moves themselves were not logged.

Later that day the encoder board was restarted for a firmware update, which sets its counts and pulse counts to zero. The operator moved each axis across its mark and homed all three: read from HAL pins afterwards, every mark was known again and every joint homed, without a fault. This is the path after a power-up of the controller, though the controller itself was not powered down.

While a program then moved X slowly across its mark, the encoder board's pulse count for X rose by about 100 in one pass: that firmware did not debounce the reference input, and one crossing was not one pulse. `refmark` only looks for a change of the count, so the "mark found" and "at mark" bits were not affected; the mark position it kept was the last of those edges and was seen between 0.040 and 0.065 mm from the point homing had stopped on. The encoder firmware was changed the same day to count the first edge only and to ignore the input until the axis has left the mark. With it, in two runs with jogs, homing and a program with arcs and a helix, every count change of X, Y and Z was by one.

The amplifier fault for homing without a known mark was seen once, on a request made while the marks were forced unknown, before CoffeeCNC refused such requests.

### Not qualified

- The LinuxCNC simulation tests were not run with this change, and there is no simulation of reference-mark homing: the refusal, the "find mark" state and the "at mark" marking are covered by unit tests of the policy, the encoders and the panel only.
- The machine-derived simulation (`run.sh -m`) has not been run on the new machine files. Its simulated hardware drops every line that names the RP2040 encoder, and `refmark_homing.hal` reads that component's pins, so it is expected to need a simulated reference mark before it loads.
- Not exercised on the machine, or not observed while it happened: the fault for an index search that overruns its mark, a homing after a real power-up of the controller, a stall during a home move, the course of a home move from each side of a mark, and Home all in one request.
- `G0759.ini` (gmoccapy) shares `custom.hal` and has not been started since that file changed.

How to read them at rest, with the machine on: `estop-ext`, `setter-ok` and `estop-ok` are on (both inputs are normally closed; off is a pressed button or a setter driven past its first contact). `setter-tripped` and `ruby-tripped` are off and go on at contact: they are the inverted inputs 19 and 18. `probe-route-ruby` is on while tool 99 is loaded and the setter is not forced. `svd-ps_vfd.*` are pins of the VFD's userspace component; while that component is not running they read "Not in HAL". `machine_config_tests` loads these twelve lines.

The HAL tools are installed on the mill (`/usr/bin/halshow`, `halmeter`, `halscope`). Each opens as a window of its own, above or below the full-screen panel as the window manager places it.
