# G0759: first machine target

The owner selected the **G0759** for CoffeeCNC's first machine integration on 14 November 2026. Machine definitions live in [tinic/linuxcnc](https://github.com/tinic/linuxcnc), separately from this application. Other machines must remain configurable without forks of the UI or controller core.

The configuration review starts from source revision [`949d67ffa6e1c5dafc2751f651297b4076fa792b`](https://github.com/tinic/linuxcnc/tree/949d67ffa6e1c5dafc2751f651297b4076fa792b/configs/G0759). The later integration results below use LinuxCNC 2.9.4 with simulated hardware. They do not establish the currently deployed configuration, physical travel, or measured tool assemblies. No hardware was contacted or operated.

## HAL and peripheral boundaries

The primary HAL loads a **Mesa 7i76E through `hm2_eth`**, with three step generators and a spindle encoder. `custom.hal` then replaces the step-generator position-feedback sources with `rp2040-encoder.0.position-{0,1,2}`; its scales are −0.005, +0.005 and +0.005. Preserve that configured feedback chain. CoffeeCNC should read LinuxCNC's resulting actual position, not derive it from step commands or talk directly to the encoder. The RP2040 userspace component must be present on the target host; its implementation is not included in this repository snapshot.

The VFD is controlled by the userspace **`svd-ps_vfd`** component on a configured serial device. The repository contains its C source. The frontend should request spindle state through LinuxCNC; device paths, maximum frequency and transport stay in the machine configuration. The existing HAL also has `not` and `limit1` components, so additional application wiring must avoid duplicate module loads and numbered-instance collisions. [Custom HAL](https://github.com/tinic/linuxcnc/blob/949d67ffa6e1c5dafc2751f651297b4076fa792b/configs/G0759/custom.hal), [VFD source](https://github.com/tinic/linuxcnc/blob/949d67ffa6e1c5dafc2751f651297b4076fa792b/src/svd-ps_vfd.c).

A physical input supplies external E-stop, and another supplies `motion.probe-input`. Spindle encoder feedback is converted from revolutions/second to RPM and absolute RPM; `spindle.0.at-speed` is driven by a `near` comparison. The embedded RPM widget consumes `spindle-vel-fb-rpm-abs`. CoffeeCNC's protocol and panel distinguish commanded RPM from optional measured RPM, at-speed and probe status. The native shell now publishes configured optional HAL feedback to the panel, with simulation coverage. Unavailable feedback remains distinguishable from a reported zero. [Main HAL](https://github.com/tinic/linuxcnc/blob/949d67ffa6e1c5dafc2751f651297b4076fa792b/configs/G0759/G0759.hal), [RPM widget wiring](https://github.com/tinic/linuxcnc/blob/949d67ffa6e1c5dafc2751f651297b4076fa792b/configs/G0759/rpm.hal).

`custom_postgui.hal` connects manual tool change to `gmoccapy.toolchange-*`, loops prepare to prepared, and refers to gmoccapy tool-offset/spindle-display pins. A CoffeeCNC-specific fragment must connect the application's manual-change handshake while preserving the intended prepare loop. Do not run both frontends' handshake outputs together. This file is reached through `postgui_call_list.hal`, so migration must follow the include chain. [Post-GUI wiring](https://github.com/tinic/linuxcnc/blob/949d67ffa6e1c5dafc2751f651297b4076fa792b/configs/G0759/custom_postgui.hal), [call list](https://github.com/tinic/linuxcnc/blob/949d67ffa6e1c5dafc2751f651297b4076fa792b/configs/G0759/postgui_call_list.hal).

## Initial findings and current integration status

The first review compared CoffeeCNC PR #6 at `7694a18` with the upstream configuration. Configuration support has since advanced:

| Finding | Current status |
| --- | --- |
| The INI has neither standard spindle ceiling key accepted by the initial loader | The derived profile explicitly supplies `[COFFEECNC] MAX_SPINDLE_RPM = 1500`. There is no generic fallback that assigns G0759 semantics to another machine's custom section. |
| Jogging used one global ceiling and omitted the configured increments | Native validation and the panel capability contract now carry per-axis ceilings and the configured increment list. |
| The initial policy always required homing | `NO_FORCE_HOMING` is now an explicit capability. Run/MDI can use this policy; active homing still blocks execution, including paused single-step. |
| The existing gmoccapy post-GUI file cannot be reused unchanged | Separate application wiring is exercised by the G0759 simulation. [Machine configuration PR #1](https://github.com/tinic/linuxcnc/pull/1) supplies a separate CoffeeCNC INI and post-GUI file; it remains a draft, without physical-machine qualification. |
| The tool table contains no cutter geometry | Assignments remain explicit. Neither a T number nor a remembered gmoccapy in-spindle value establishes physical geometry or controller state. |

`NmlPort` currently fills `Axis.machine` from `motion.traj.actualPosition`, normalized to mm. The preview anchors the tool body at that value minus the active tool offset once, matching the protocol's tool-tip convention. Work-origin transforms and the cutter's physical overall length do not enter this anchor.

## Keep machine support extensible

Use these boundaries for the next implementation:

1. **LinuxCNC remains the configuration authority.** Load axes, kinematics, units, limits and state from the selected INI/controller. A machine integration profile records any explicit custom-key mappings, optional signals and extra UI features; ordinary widgets consume capabilities rather than machine names.
2. **Keep launch/HAL integration separate.** The G0759 owns its Mesa, encoder, VFD and physical input wiring. CoffeeCNC owns its application pins and handshake contract. Preserve the gmoccapy setup alongside a separately reviewable CoffeeCNC configuration.
3. **Scope persistence by machine identity.** Native tool-model assignments, job attachments and preferences need a stable configuration identity, not just `MACHINE = G0759` or a T number. Physical stick-out is also setup-specific. Browser-only defaults remain a development convenience.
4. **Advertise only implemented capabilities.** Initially support XYZ identity kinematics and manual tool changes. Other machine layouts should produce a specific unsupported-capability explanation. Later rotary axes, gantries, tool changers and spindle orientations require richer contracts, not hidden G0759 assumptions in the renderer.
5. **Qualify a derived simulation first.** Exercise the G0759's units, asymmetric rates, increments, overrides, empty-dimension tool table and manual-change flow in a hardware-free fixture. Do not launch the real HAL in tests: it loads network and serial hardware drivers. Retain the worker/lease and delayed-jog-start tests before live-shell wiring.

## Implemented simulation baseline

[PR #10](https://github.com/tinic/coffeecnc/pull/10), merged as `e74339b`, adds the G0759-shaped simulation and native configuration coverage. The loader reads axis jog ceilings, jog increments, overrides and `NO_FORCE_HOMING`; the derived profile explicitly sets `[COFFEECNC] MAX_SPINDLE_RPM = 1500`. It declares optional spindle-RPM, at-speed and probe signals through CoffeeCNC configuration and HAL pins. These settings do not alter the upstream machine configuration or load its hardware drivers.

The native policy rejects single-step while homing is active even when homing is not required. Session now always uses a `ProgramStore`; there is no unchecked program-open constructor. The shared [protocol fixtures](../../protocol/fixtures/messages.json) cover the corresponding capabilities, nullable feedback and partial program/directory snapshots. The native shell connects adapter status to these messages and delivers them to the panel.

The profile refuses **Home all** because no `HOME_SEQUENCE` is configured. Its simulation tests home axes individually at their current position; this does not seek a home switch or establish a measured physical origin. The simulated main HAL loads the existing `not` and `limit1` instances before CoffeeCNC's fragment, which uses `watchdog` and named `lut5` instances without reloading those modules. See the [G0759 simulation HAL](../../backend/tests/sim/coffeecnc_g0759_sim.hal) and [CoffeeCNC post-GUI fragment](../../backend/tests/sim/coffeecnc_g0759_postgui.hal).

Claude reported **13/13 development CTests** on playhouse2 with LinuxCNC 2.9.4 at the integration head: portable behavior, machine configuration, metric/inch/G0759 simulations and cleanup-runner regressions, with zero LinuxCNC processes remaining. This is simulation evidence. Physical homing behavior, travel and tool measurement remain commissioning questions.

## Runtime and native shell verification

[PR #11](https://github.com/tinic/coffeecnc/pull/11), merged as `9d16064`, adds separate command, status and HAL control threads. The control thread maintains heartbeat and jog leases without waiting for NML. A jog stop remains asserted until delayed starts have returned and later stop commands have been accepted. Release, page teardown, cancellation and shutdown are covered, including a frozen LinuxCNC task that cannot immediately answer commands. The initial stop signal affects all axes: releasing one held axis stops all held axes, and further motion requires a fresh press.

On playhouse2 with LinuxCNC 2.9.4, code head `627bd8a` passed **15/15 CTests in each of the development, analysis, AddressSanitizer and ThreadSanitizer presets**. The final PR commit added documentation only. All four presets include metric, inch and G0759 simulations and runner cleanup checks. Codex independently reviewed the retained logs; the portable predecessor also passed 9/9 tests in a clean macOS export, with no portable source changes in `627bd8a`. These results qualify the tested simulation behavior, not physical hardware or a hard real-time deadline. Sanitizer coverage does not extend to uninstrumented distribution libraries or the external LinuxCNC realtime process.

[PR #12](https://github.com/tinic/coffeecnc/pull/12), merged as `ba41d78`, adds the GTK/WebKit executable, adapter-to-panel status mapping and live message delivery. Native simulation checks cover the local scheme, STEP worker/WASM, automated file-chooser delivery, WebGL2, tool-model editing and page reload. The retained results and sanitizer limits are in [native WebKitGTK qualification](../research/step-preview.md#native-webkitgtk-qualification); GUI ThreadSanitizer and accessibility-enabled leak behavior remain unqualified. These checks do not establish physical G0759 operation.

Interpreter-backed preview is implemented in [PR #15](https://github.com/tinic/coffeecnc/pull/15). Native STEP overlays use its matching program context; the [preview evidence](../research/evidence/native-preview-a114848-review.txt) records tested samples and interpreter limitations. The panel honors the [capability fields](../../protocol/README.md) and presents measured RPM, at-speed and probe feedback with explicit unavailable/stale states; the browser simulator reports no sensor measurements. Native tool-model persistence is under review, with editor save and full LinuxCNC/application restart tests recorded in the [storage review](../research/evidence/native-tool-models-61fdc34-review.txt).

## Separate launch configuration and E-stop observations

[Machine configuration PR #1](https://github.com/tinic/linuxcnc/pull/1), reviewed at `e11000c`, adds `G0759-coffeecnc.ini` and `coffeecnc_g0759_postgui.hal`. Existing machine files remain unchanged. The new INI selects CoffeeCNC, supplies the spindle limit and optional feedback signals, and declares `[COFFEECNC] MACHINE_ID = g0759` for per-machine settings. The gmoccapy configuration remains a separate launch choice.

The machine-derived simulation uses these INI/HAL files with the hardware driver connections replaced by simulated feedback. At CoffeeCNC `69880e8`, development and Release runs exercised software E-stop requests and external-input changes while idle, jogging, and running a program with the spindle commanded on:

| Action in the simulation | Observed result |
| --- | --- |
| Software E-stop request with the external input closed | Motion ends, spindle command turns off, interpreter becomes idle, and sampled machine state changes from ON to OFF. The requested ESTOP state is unconfirmed; the command result remains failed and says that LinuxCNC reports machine off. |
| External E-stop input opens | Sampled machine state changes to ESTOP; motion and the spindle command stop. |
| Machine on after the software request | ON is accepted, but `iocontrol.0.user-enable-out` remains false. A subsequent power-off also leaves it false. |
| Reset requested while already OFF | `iocontrol.0.user-enable-out` becomes true. Power-on is a separate action. |

In the tracked G0759 HAL, the external input drives `iocontrol.0.emc-enable-in`; the signal driven by `iocontrol.0.user-enable-out` has no consumer. These observations must not be generalized to another machine's E-stop wiring. The application uses reported state and configuration rather than a `G0759` name check.

The panel change at `579ccfd` makes **Reset E-stop** available while OFF as well as ESTOP, alongside the separate **Machine on** action. It is awaiting the combined native integration check. The backend review also identified that cached status must not confirm an E-stop request after the controller stops publishing; that correction remains pending at this checkpoint. The [packaging review](../research/evidence/native-package-69880e8-review.txt) records the passing runs, open finding and exact scope. State sampling does not establish physical stopping latency or continuously exclude a transient state between samples.
