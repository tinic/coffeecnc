# CoffeeCNC operator panel

Vue 3 / TypeScript panel using the [original CoffeeCNC concept](../docs/concepts/coffeecnc-mill.html) as its visual base. The browser simulator is separate from LinuxCNC and is labeled throughout the interface.

```sh
npm ci
npm run dev
```

Open `http://127.0.0.1:5174/?scene=running&tab=program&theme=light`. Use `theme=dark` for the other theme. `tab=manual` and `tab=tools` select the other workspaces; view changes do not request a machine mode change. The default view of a program is its toolpath, with Code and Split available explicitly.

```sh
npm run check
npm run build
```

The 250 tests cover the protocol fixtures, simulator, interpreter, store, camera, units, jog lease, STEP mesh validation, model placement/import lifetime, parametric tool envelopes, default inheritance tool-model editor behavior, loaded-tool identity/position gating, capability-aware jog/execution controls, protocol-mismatch handling, program unload/reload identity, and partial text/directory presentation. The shared native message fixture has 26 cases checked against TypeScript and the C++ encoders, including null versus zero/false and partial snapshots. Preview regressions cover changed initial position, inherited motion mode and prepared tool, while retaining a stable context during execution. Work-offset component tests cover explicit availability, real zeros, older complete tables, stale/down readings, malformed rows and operator-triggered selection. Transport tests cover browser simulation, a missing or malformed native handler, and native request/reply delivery. Held-jog regressions cover stale/silent status, power loss, E-stop, busy/homing state, homed-space changes, local answer timeout and synchronous refusal. An interrupted gesture requires a new press after recovery. The visual correction was also exercised in the browser: cycle start, manual tool acknowledgment, hold/resume, Stop, view switching while paused, and a held jog followed by release and zero feed. These are simulator checks, not machine validation.

The browser preview shows toolpaths, an optional STEP part layer and a configured loaded-tool envelope. The native GTK/WebKit executable now runs this panel against LinuxCNC simulation; STEP import and the tool-model editor have native checks, while the part overlay waits for native interpreter preview. Stock removal and hardware operation remain separate increments. Tool sequence labels come from interpreter segments and the tool table; they are not assumed CAM operations or claims of measurement. Fonts are bundled under `public/fonts/` with their licenses. See [native build instructions](../backend/README.md) and [qualification limits](../docs/research/step-preview.md#native-webkitgtk-qualification).

In Machine, use **Attach STEP model → Choose STEP file…**. The simulator also offers an SM-101 sample, explicitly labeled as not paired with the demo NC program. Import runs in a dedicated worker; Three.js renders a translucent mesh beneath the toolpath using the same orbit/pan/zoom camera. The importer and renderer load on demand from local assets. WebGL 2 is required for the optional part/tool meshes; the 2D toolpath remains available without it.

The model starts at the current work origin with placement marked unconfirmed. Edit XYZ translations in millimeters and XYZ rotations in degrees, then **Apply placement**; this changes only the display. Visibility and opacity are independent of the toolpath. Registration is captured against the program revision, WCS, G5x, G92 and XY rotation; changed work coordinates hide the model until placement is reviewed. Reloading/changing the program removes it. Attachments are page-local and are not saved across page reloads.

Imports are limited to 25 MB, 500,000 triangles and 800,000 vertices, with a 30-second deadline and cancellation. These are input/output limits, not a hard WASM heap quota. Failure preserves the previous attachment. Run `npm run check:step` to exercise the real WASM importer against all 29 repository STEP samples, including centimetre/inch source-unit checks against documented physical sizes. See [the library comparison and integration boundary](../docs/research/step-preview.md) and [third-party notices](THIRD_PARTY.md).

In Tools, **Model defaults** configures nominal proportions for seven tool families. **Set model** on a row selects a family and optional absolute dimension overrides, with a live WebGL 2 envelope preview. Family defaults persist in browser storage; per-tool assignments are page-local and invalidated by changed/deleted rows or a new connection hello. The editor supports mm/inch display, keeps physical dimensions independent of controller Z offsets, and does not issue controller commands. Production-browser checks covered saved defaults across reload, diameter scaling, overrides, the 1280 × 800 layout and a narrower viewport. See [the geometry and storage contract](../docs/design/tool-models.md). The Machine preview places the configured loaded tool at its reported tip and shares the STEP camera. Browser checks covered tool visibility, combined STEP/tool rendering and motion followed by feed hold at 1280 × 800. Native configuration persistence remains a subsequent increment.

Codex owns the visual components and styles; Claude owns the C++ backend and behavior review. See [implementation alignment](../docs/design/implementation-alignment.md) for the visual acceptance criteria. Representative 1280×800 captures are in `screenshots/`.

The additive v1 [machine-capability fields](../protocol/README.md) let the panel honor per-axis jog ceilings and an explicit homing requirement. Older peers keep the original behavior. Keyboard step/hold tests verify clamped outbound requests and release on a changed hello; simulator tests verify actual asymmetric jog movement and MDI/program homing gates. The native mapper publishes these capabilities and optional spindle/probe feedback from the configured LinuxCNC/HAL inputs.

The native `coffeecnc://panel/` page requires its WebKit message handler. If the handler is missing or invalid, requests are refused locally with a connection error, and no simulated machine state appears. Ordinary browser development continues to use the labeled simulator. A native handler is selected when available; it must be installed before the page loads.

Work offsets with `available: false` show dashes and Unavailable. Known stale values remain labeled as history; disconnected placeholders are withheld. [The work-offset screenshot](screenshots/work-offset-availability.jpg) uses an injected protocol fixture against the production bundle, checked in light/dark themes at 1280 × 800 with selection and lower-row scrolling. It is a browser display check, not a native LinuxCNC session.

Measured spindle speed and at-speed feedback appear in the Machine status strip and beside the Manual spindle controls; Manual also shows the probe input. Missing readings say **Unavailable**. Zero RPM, **No** and **Clear** remain actual readings; stale/silent values carry a visible **stale** suffix, while down/incompatible/connecting values are withheld. Readings never come from spindle commands. The browser simulator has no sensors and reports them unavailable. Twelve component regressions cover these distinctions.

Production-browser verification at 1280 × 800 covered light/dark Machine views, Manual layout, resume/feed hold/Stop and held-jog release; no whole-page scrolling or browser-console warnings/errors were observed. Screenshots: [Machine feedback](screenshots/spindle-feedback.jpg), [dark Machine feedback](screenshots/spindle-feedback-dark.jpg), [Manual feedback](screenshots/manual-feedback.jpg).

The job bar offers **Dismiss** for error messages; the message remains in the session log. Dismissal changes no controller state or preview error. The production browser check confirmed dismissal and retained history at 1280 × 800, with Stop and E-stop visible and a clean console: [error dismissal](screenshots/error-dismissal.jpg).

The program footer prioritizes E-stop, machine-off and homing states over idle or paused labels. Live line progress and NC highlights require fresh status, matching program text and active AUTO execution. Idle shows the supplied file's line count; MDI and stale counters do not highlight the loaded program. Partial text and out-of-range counters have no progress denominator, and counters are never clamped to an unrelated row. Fifteen focused snapshot/status tests passed, along with type checking, lint and the production build.
